# 新增、更新、维护与审计流程

## 目录

1. 捕获与分流
2. 新增实体和事实
3. 新增知识
4. 更新与冲突处理
5. 项目知识晋升
6. 周期性维护
7. 归档和迁移
8. 审计清单

## 1. 捕获与分流

无法在短时间内判断归属的内容先进入 `inbox/`，并至少记录：

- 捕获日期；
- 原始内容或来源；
- 为什么可能有价值；
- 可能关联的项目或实体；
- 下一步处理动作。

Inbox 是缓冲区，不是永久分类。维护时逐项采取：删除无价值副本、登记事实、保存来源、写入项目、提炼知识或继续等待证据。

## 2. 新增实体和事实

1. 使用名称、别名、型号、序列号和相近 ID 全库检索。
2. 判断记录的是类型、型号、实物、组织、项目还是其他对象。
3. 从相应前缀中分配未使用 ID；不得填补或复用已归档 ID。
4. 在 `entities.csv` 中写入通用字段。
5. 在领域登记表或对象目录中写入专用字段和说明。
6. 保存证据路径、观察日期和验证日期。
7. 添加与项目、型号、组织、位置、方法或来源的关系。
8. 更新导航并运行审计。

用户直接陈述“我拥有某设备”可以作为当前登记依据，但要在证据或说明中标注为用户陈述；不要虚构序列号、购买日期或位置。

## 3. 新增知识

先选择内容类型：

- `concept`：回答“是什么、为什么”；
- `method`：描述可复用的分析或实验方法；
- `protocol`：给出可执行步骤和验收条件；
- `troubleshooting`：症状、原因、诊断和修复；
- `lesson`：跨项目经验及适用边界；
- `reference`：参数、字段或稳定事实的查阅表。

新增前搜索同义词和相关概念。优先扩充已有条目；只有独立引用和复用能明显受益时才拆分新条目。

每个正式知识条目至少包含：

- 清晰标题和永久 ID；
- 一句话摘要；
- 适用范围；
- 主体内容；
- 限制或反例；
- 来源或项目证据；
- 相关实体和知识；
- 状态、创建日期、验证日期和更新日期。

不要把来源摘录直接当作自己的结论。区分：来源说了什么、项目观察到什么、当前综合判断是什么。

## 4. 更新与冲突处理

### 普通更新

1. 找到字段的权威位置。
2. 核实新信息的证据和有效时间。
3. 修改权威值和 `updated_at`；实际重新核实才修改 `verified_at`。
4. 检查依赖它的项目、关系和生成视图。
5. 记录重要变更原因。

### 冲突事实

1. 不静默覆盖任一方。
2. 比较来源类型、产生时间、观察方法和适用条件。
3. 如果事实具有时间变化，使用有效期而不是判定其中一方错误。
4. 若能解决，更新当前权威事实并保存旧值的历史。
5. 若不能解决，标记冲突、保留两份证据并创建待核实事项。

### 重复实体

1. 证明两个 ID 指向同一现实对象。
2. 选择保留 ID，通常采用引用最多或创建最早的 ID。
3. 将关系和引用迁移到保留 ID。
4. 保留废弃记录并写入 `superseded_by`/`supersedes` 关系。
5. 不删除导致旧链接失效的最后线索。

## 5. 项目知识晋升

项目材料按照以下成熟度流动：

```text
observation → candidate → validated → reusable → deprecated/archived
```

晋升检查：

- 是否经过重复实验、独立来源或明确复核；
- 是否能表述成项目之外仍成立的概念、方法或经验；
- 是否保留了适用条件、失败条件和不确定性；
- 是否链接原始实验、数据、决策和来源；
- 是否与已有通用知识重复或冲突。

晋升时新建或更新 `knowledge/` 条目，添加 `origin_projects` 和来源；项目原记录保持不变。

## 6. 周期性维护

### 每次写入后

- 运行结构审计；
- 检查新增 ID、路径和关系；
- 更新相关入口；
- 汇报无法确认的信息。

### 每周或每两周

- 处理 `inbox/`；
- 检查活动项目入口和即将失效的事实；
- 修复断链、重复和未分类来源；
- 查看是否存在可晋升的项目知识。

### 每月或每季度

- 核实设备、软件、许可证、组织联系人和活动项目状态；
- 复查长期未验证的客观事实；
- 检查通用知识是否被新证据推翻；
- 归档完成项目和过时材料；
- 评估词汇、类型和自动化是否仍然必要。

维护频率应由变化速度和风险决定，而不是所有内容采用同一周期。

## 7. 归档和迁移

归档记录至少保留：ID、名称、最终状态、原路径、归档时间、原因、替代对象和关键来源。完成项目的摘要、决策和最终报告应保持可检索。

大规模迁移前：

1. 建立旧路径到新路径的映射；
2. 先做只读审计和迁移计划；
3. 在小范围样本上验证；
4. 保留可恢复副本或版本历史；
5. 更新关系、导航和 `canonical_path`；
6. 迁移后重新审计。

未经用户明确授权，不做批量删除或不可逆重命名。

## 8. 审计清单

自动检查：

- 必需目录和中央表是否存在；
- CSV 表头和行结构是否正确；
- ID 是否唯一且符合格式；
- 项目是否同时具有实体记录和项目扩展记录；
- 关系两端是否存在；
- 权威路径和证据路径是否有效；
- 日期格式是否正确；
- 活动记录是否长期未验证；
- 知识和项目入口是否具有核心元数据。

人工检查：

- 同义词造成的语义重复；
- 同名不同物和型号/实物混淆；
- 项目结论被误当作通用事实；
- 来源、观察和综合判断混写；
- 过度拆分、过度标签和无用途属性；
- 已失效但仍被引用的知识；
- 没有入口的孤立内容；
- 敏感信息和不应进入知识库的凭据。
