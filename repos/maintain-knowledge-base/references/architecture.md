## 1. 设计目标

默认架构需要同时支持：

- 精确回答“有多少、是什么状态、在哪里、属于谁”；
- 管理科研项目的实验、数据、方法、结果和报告；
- 管理事务项目的背景、沟通、决策、材料和结果；
- 把项目中验证过的经验沉淀为跨项目知识；
- 让人和 Agent 都能通过普通文件工具读取；
- 在没有专用笔记软件或向量数据库时仍然可用。

## 3. 五个信息层

### 事实层

保存对象身份、类型、状态、位置、版本、负责人和验证日期。事实必须可统计，并明确权威字段的维护位置。

### 关系层

用稳定 ID 表示 `uses`、`produces`、`applies`、`derived_from` 等关系。关系本身也要允许记录上下文、有效期和证据。

### 通用知识层

保存概念、解释、方法、协议、排障和跨项目经验。以用途或概念为中心，而不是按来源或项目重复写同一主题。

### 项目层

科研项目保存问题、假设、实验、数据、分析、结论和限制；事务项目保存目标、利益相关方、沟通、材料、决策、结果和后续义务。

### 来源层

保存论文、手册、标准和其他外部材料。来源是证据，不自动成为知识。知识条目必须说明从来源中提炼了什么。

## 4. 检索路径

| 用户问题 | 首选入口 | 后续路径 |
|---|---|---|
| 有多少个某类对象 | `catalog/entities.csv` | 按类型、子类型和状态过滤 |
| 某对象的规格或历史 | 实体登记 → `canonical_path` | 对象说明、来源、相关项目 |
| 正在进行哪些项目 | 活动项目视图 | `PROJECT.md`、关系表 |
| 项目使用了什么 | 项目入口 | `relations.csv` → 对象目录 |
| 某方法如何执行 | `knowledge/methods` 或 `protocols` | 来源、采用项目、限制 |
| 某结论从哪里来 | 知识条目 | 项目证据 → 外部来源 |
| 某事务为何这样决定 | 项目决策记录 | 背景、选项、影响和后续结果 |

目录设计必须服务高频检索问题。不要仅为了视觉对称增加层级。

## 5. 扩展规则

- 新增 `domains/<type>/` 前，确认至少存在多个长期对象或明确的高频查询。
- 新增实体类型时，同时更新 `vocabulary.md`、ID 前缀和必要模板。
- 新增关系词前，确认现有关系无法准确表达；给出方向、含义和示例。
- 领域专用字段放在领域登记表或对象说明中，不不断扩张通用 `entities.csv`。
- 大型数据、敏感资料或专用二进制文件可以外置，但必须保留路径、校验值、权限和来源说明。
- 可生成搜索索引、向量索引或网页视图，但这些都是可重建的派生物。

## 6. 反模式

- 从项目文件夹数量推断资产数量；
- 同一状态在中央表、项目文件和设备说明中分别手工维护；
- 把整篇论文摘要直接当作自己的知识结论；
- 给每个句子创建独立笔记，导致上下文破碎；
- 只依赖标签或全文搜索，不建立权威入口和明确关系；
- 为了保持目录整洁而删除历史项目或复用旧 ID；
- 将待办、聊天片段、来源、事实和结论全部混在一个文件中；
- 在没有用途的情况下持续增加属性、插件和自动化。
